## Findings

- **P1 — Entropy scan-bypass via Unicode case-folding keyword variants (attempt-5 regression).**
  The merged presence automaton is built with `ascii_case_insensitive(true)` over byte patterns (engine.rs:331–334, patterns from `merged_presence_keyword_buckets`, engine.rs:99–124) and its verdict gates the entropy detector: `if self.entropy_keyword_ids.iter().any(|&id| presence[id]) { … detect_near_keywords_proven(…) }` (engine.rs:582–590). But the entropy keyword regex is Unicode-case-insensitive (`(?i)\b(…)\b`, entropy.rs:94) and the regex crate (1.13.1) simple-case-folds U+017F ſ→s and U+212A K→k, so regex-matchable keyword spellings exist whose bytes the ASCII-only automaton can never see. On those payloads the gate proves "absent", the detector is skipped, and a real high-entropy secret near a folded keyword is silently lost. Empirically confirmed on the shipped CLI (V1/V2/V4) and differentially proven against base `fccd9e4` (which ran the same regex unconditionally — base engine.rs:286). The builder's core claim "Presence proofs are one-way — a miss proves absence" is **false** for this class. The context-keyword path already implements the correct conservative guard (`!context.is_ascii()`, engine.rs:437, 651–658); the entropy path lacks the mirror guard. Suggested fix direction (for the fix plan, not applied here): run the entropy detector unconditionally when `!text.is_ascii()` (or fold fold-to-ASCII code points into the automaton). Fix command target: `crates/cerberus-engine/src/engine.rs:582` + a new test analogous to `context_prefilter_unicode_fallback_preserves_casefold_and_boundaries`.

- **P2-1 — `extract_prefix` mangles non-ASCII literal prefixes (pre-existing at base; parity-neutral).**
  `prefix.push(bytes[i] as char)` (engine.rs:55) re-encodes each UTF-8 byte as a Latin-1 char, so the AC pattern bytes differ from the regex's literal bytes; a user rule whose pattern starts with a non-ASCII literal (length ≥ 2) is silently dead (fail-open at rule-authoring time). Same behavior at base (verified via `git show fccd9e4:…`), so findings parity is preserved — but the criterion "patterns whose prefixes are non-ASCII are NOT answered by an ASCII-only automaton / conservative fallback must scan them anyway" is not met for pattern prefixes. Not an attempt-5 regression; recorded because it is in the candidate's diff scope and security-relevant.

- **P2-2 — `KNOWN_SAFE_EXAMPLES` exact-value detection carve-out introduced in attempt-5's commit (`4683dd4`), undocumented in the F1.3 pack.**
  entropy.rs:62 hard-allowlists `wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY` (entropy.rs:186 skips it before the entropy check). Any value exactly equal to that public AWS documentation string is never reported. Attack value is negligible (the string is public), and the production suite apparently relies on it (`canonical_public_aws_example_is_not_a_secret`), but a deliberate detection gap should be declared in the evidence pack — it currently is not.

- **P2-3 (informational, from R9-9 commit `786c576`, not attempt 5) — context keyword word-boundary semantics are looser than regex `\b`.**
  constraints.rs:31 returns `is_word_char('_') == false`, so `_phone` / `phone_` count as word-bounded keyword occurrences. This only widens context admission (over-redaction direction); the automaton/analyzer one-way property is unaffected.

No other P0/P1/P2 findings from the attempted vectors.

## Final verdict: FAIL

Failing criterion: **scan-bypass reasoning + payloads (merged case-insensitive presence automaton)** — P1 above.

The security lens confirms the attempt-5 machinery is well-built where it was audited hardest: all five gates pass with exact counts (clippy clean; ReDoS release 11/11; engine 232/232; json_redact 5; production pack 19/19), the U+0130/Unicode context fallback is preserved (focal test passes), the entropy fail-open invariant survives (visible panic, no cached no-findings state), the JSON analyzer path is parity-sound, the PAN/automaton hot path survived a 13-payload adversarial battery without panics or quadratic behavior, no secret material is logged, and the workload fingerprints are asserted in both profiles with frozen file hashes matching the pack. But the one-way-presence claim that the whole optimization rests on is violated for entropy keywords: an ASCII-case-insensitive automaton cannot prove absence for keyword spellings that Unicode simple case folding makes matchable (`ſecret=…`, `<U+212A>ey=…`), and the shipped CLI demonstrably returns "No sensitive data detected" for payloads that the base engine detected — a real, cheaply-exploitable detection regression in the exact dangerous direction (presence miss ⇒ skipped detector ⇒ lost finding). Fix is small (mirror the context path's `is_ascii` conservative guard) and the unit must return to FIX; the other criteria do not need re-adjudication beyond re-running the suite matrix after the repair.
