## 3. Card regex review (default_pack.rs:149) — NO ReDoS, PASS

`(?:\+[0-9](?:[ -]?[0-9]){12,}\b|\b[0-9](?:[ -]?[0-9]){12,}\b)` — unbounded `{12,}`.
- Rust `regex` is a linear-time NFA/DFA engine; no backtracking exists, so the unbounded quantifier cannot blow up combinatorially. Measured (release, full pack, engine.scan): 10KB 0.10ms → 100KB 0.91ms → 1MB 9.1ms; ratios 8.99 / 10.01 for 10× inputs — linear.
- Digit-only run 1MB: 2.1ms; dash/space alternating 1MB: 9.8/9.1ms; non-terminating `\b` groups 1MB: 2.6ms; dangling separator runs 560KB: 8.3ms.
- Oversized matches (up to haystack size) are rejected by `maxLength=38` in `check_constraints` **before** validators run (engine.rs:334–337), so `luhn_valid`/`payment_card_valid` (both O(|match|) allocations) never see megabyte inputs from the shipped pack. Ordering verified and is the correct defense; document it as an invariant (rules pairing an unbounded pattern with a validator MUST set maxLength, else validator-side O(n) allocation on attacker-controlled match length).

## 4. BLOCKER 1 — CRITICAL availability: entropy window slices a non-char boundary → panic-DoS

`crates/cerberus-engine/src/entropy.rs:138-139`:
```
let search_end = std::cmp::min(kw_end.wrapping_add(NEAR_KEYWORD_WINDOW), text.len());
let context = &text[kw_end..search_end];   // panics if 200-byte edge lands inside a multibyte char
```
PoC via the public product API (release, exact panic location `entropy.rs:139:28`):
```
let mut p = String::from("key="); p.push_str(&"x".repeat(197)); p.push('€');
engine.scan(&p);  // thread panicked: end byte index 203 is not a char boundary; it is inside '€' (bytes 201..204)
```
- The entropy detector is a **virtual rule that always runs** in every `CompiledEngine::scan` (engine.rs:312–319); the keywords list includes extremely common short words (`key`, `auth`, `token`, `hash`, `salt`, `private`). Any body containing one of these words followed ~200 bytes later by a multibyte character (€, emoji, CJK, accents — trivially attacker-crafted, also reachable accidentally by legitimate EU/Asian traffic) panics the scan.
- Impact: per-request crash/connection death in the proxy hot path; no `catch_unwind` exists anywhere in crates/cerberus-proxy or crates/cerberus. Fail-safe is NOT guaranteed (a panicking task in a streaming/JSON-redact flow can bypass fail_policy error propagation).
- Test coverage: neither `tests/redos_fuzz.rs` nor entropy unit tests exercise multibyte payloads near the 200-byte window edge. This is in the frozen file set for attempt 4, i.e., F1.2 scope.
- Fix direction (for builder, not applied here): `let search_end = text.floor_char_boundary(min(kw_end+NEAR_KEYWORD_WINDOW, text.len()))` (stabilized `floor_char_boundary` on 1.97? — otherwise manual byte-walk back while `!text.is_char_boundary(e)`), plus a multibyte regression test in entropy.rs and redos_fuzz.

## 5. BLOCKER 2 — HIGH performance: per-match full-context normalization → quadratic scan for a shipped-pack input class

`crates/cerberus-engine/src/constraints.rs:42-46`: for every match of a rule with `contextKeywords`, `let ctx_lower = context.to_lowercase()` allocates and lowercases the **entire context** (in `scan()` context == full text), then `contains` scans it. Shipped pack rule `pii.phone_number` (default_pack.rs:163-173) has keywords and matches every 7–15 digit token — phone-list/CSV-shaped payloads are a core product use case.

Measurements (release, `engine.scan`, M4 Pro):
```
phone-list "contact list:\n" + "1234567 "×N   matches    p50
50 KB                                          ~6.2k      41.7 ms   (budget p99 3–5 ms → 8–14× over)
100 KB                                         ~12.5k     194.8 ms  (worst sample 658 ms)
320 KB                                         ~40k       0.39–2.9 s (keyword present/absent)
1.28 MB                                        ~160k      6.0–49.1 s; 4× size → ~16× time = quadratic
```
Root-cause attribution (single-rule engines): card rule alone 640KB→0.8ms; phone-no-keyword rule alone 640KB→1.3ms (both linear); keyword-phone rule alone 320KB→738ms; same rule with `contextKeywords:[]` 320KB→15.7ms. The regex is linear; the **engine scan path is not** because of per-match O(|text|) work.
- The fix plan (§0.1 R9-1) already marks repeated context normalization VERIFIED but schedules the repair under F2.1 for the JSON path. This probe shows the same quadratic cost is reachable through the plain-text `CompiledEngine::scan` used by CLI/daemon/entropy-free paths; it directly breaks §5 "p99 < 3–5 ms" at 50 KB and F1.3's "< 1 ms per 100 KB" gate (100 KB digit-dense ≈ 195 ms). It should be fixed with F1 scope (precompute normalized context once per scan in `CompiledEngine` / `scan_with_context`, and/or check length/allowedExamples ordering before keyword normalization), not silently deferred to F2.1.
