## FINDING SEC-1 (Medium) — mixed separator styles inside one PAN are suppressed

The attempt-6 matcher partitions a separator-connected digit run at every
**separator-kind change** (`partition_payment_card_run`, engine.rs:694-704,
`separator_changed` branch). A PAN formatted with more than one separator style is
split into segments below 13 digits and the whole run is then rejected — while the
attempt-5 regex (and even the attempt-6 regex path) matched the whole PAN.

Exact repro (shipped engine, `cargo run --release` in the probe crate):

```text
"pay 4111 1111-1111.1111"            (PAN 4111111111111111, Luhn+Visa valid)
  attempt-6 shipped matcher: 0 card findings   ← suppression
  attempt-6 regex path:      pii.credit_card @ 4..23
  attempt-5 regex (blessed): pii.credit_card @ 4..23
"pay 4000.0566-5566 5556"            (PAN 4000056655665556)
  shipped: 0 findings; regex path + attempt-5: pii.credit_card @ 4..23
"pay 4111\u{a0} 1111 1111\u{a0}1111" (NBSP/ASCII mixed)
  shipped: 0 findings; regex path + attempt-5: pii.credit_card @ 4..23
```

Probe check names: `pan[R8_mixed_styles_within_pan]`, `pan[R9_mixed_styles_2]`,
`pan[R10_mixed_nbsp_ascii]`. The final log prints the three-way differential
verbatim (all assertions pass — the divergence itself is the evidence):

```text
DIFF R8_mixed_styles_within_pan text="pay 4111 1111-1111.1111"
     shipped=[] regex_path=Some([(4, 23)]) attempt5_regex=Some([(4, 23)])
DIFF R9_mixed_styles_2 text="pay 4000.0566-5566 5556"
     shipped=[] regex_path=Some([(4, 23)]) attempt5_regex=Some([(4, 23)])
DIFF R10_mixed_nbsp_ascii text="pay 4111\u{a0} 1111 1111\u{a0}1111"
     shipped=[] regex_path=Some([(4, 26)]) attempt5_regex=Some([(4, 26)])
```

Why it matters: single-style separators (all-dots, all-slashes, all-NBSP,
all-double-space, per-digit, `+`-prefixed) remain detected (verified), so the
regression is confined to **style mixing within one PAN** — but that is exactly the
class the attempt-5 security report verified as fixed ("mixed separators … are all
detected as `pii.credit_card`"), and the attempt-6 gate tests only cover
single-style shapes, so the gate cannot see it. Suppression is total: the PAN also
never re-classifies as a phone (`pan[...]​/full_suppression_check` asserts empty
phone spans on every suppressed case — pass), so `pii.credit_card` (critical,
redact) silently does not fire.

Suggested fix direction (for the builder, not applied): only split a run at a
separator change when BOTH sides are independently complete valid PANs (extend the
`separates_two_unformatted_runs` condition with the kind-change test), or attempt a
segment-split validation before rejecting the run.

## FINDING SEC-2 (Low) — No-category Unicode chars adjacent to a PAN suppress it

The matcher emulates `\b` with `char::is_alphanumeric()` (engine.rs:505-514,
545-548). The regex crate's `\w`/`\b` word class is
`Alphabetic ∪ M ∪ Nd ∪ Pc ∪ Join_Control` — it excludes **No** (other numbers:
`½` U+00BD, `²` U+00B2, `º`, circled digits), which `is_alphanumeric()` DOES treat
as word characters. A PAN glued to such a char is found by both regex baselines and
missed by the matcher:

```text
"4111111111111111\u{00bd}"  shipped: 0 findings; regex path + attempt-5: card @ 0..16
"\u{00bd}4111111111111111"  shipped: 0 findings; regex path + attempt-5: card @ 2..18
"4111111111111111\u{00b2}"  shipped: 0 findings; regex path + attempt-5: card @ 0..16
```

Probe checks: `pan[R12..R14]`; log lines:

```text
DIFF R12_vulgar_fraction_after_pan  text="4111111111111111\u{00bd}" shipped=[] regex_path=Some([(0,16)]) attempt5_regex=Some([(0,16)])
DIFF R13_vulgar_fraction_before_pan text="\u{00bd}4111111111111111" shipped=[] regex_path=Some([(2,18)]) attempt5_regex=Some([(2,18)])
DIFF R14_superscript_two_after_pan  text="4111111111111111\u{00b2}" shipped=[] regex_path=Some([(0,16)]) attempt5_regex=Some([(0,16)])
```

Attacker-controllable, obscure, and single-char; grade Low. The inverse divergence (combining mark U+0301 / ZWJ U+200D after a PAN:
matcher FINDS, regex does not) is FP-direction — `pan[R15..R16]`, informational,
fail-safe.

## FINDING SEC-3 (Low, PRE-EXISTING since fccd9e4) — AC prefilter mojibake kills custom rules

`extract_prefix` pushes pattern bytes ≥ 0x80 as `char` (`prefix.push(bytes[i] as
char)`, engine.rs:46-48,55): a non-ASCII literal in a rule pattern produces a
UTF-8-re-encoded **mojibake** prefix (é → `Ã©`). The Aho-Corasick prefilter then
requires bytes that never occur in text containing the real character, so the
pattern's regex is never evaluated and the rule is **silently dead**:

```text
rule pattern "café-[A-Za-z0-9]{8,}"  scan "café-abcdefgh12345"  → 0 findings (suppressed)
control pattern "(?:café)-[A-Za-z0-9]{8,}" (unprefixed → regex always runs)
                                     scan "café-abcdefgh12345"  → finding (fires)
```

Probe checks: `PF1_unicode_literal_rule_matches` (the single failing check —
intentional; log: `plain-rule found=false control found=true`),
`PF2_ascii_custom_rule` (ASCII custom rules healthy). Verified
pre-existing: `git show fccd9e4:crates/cerberus-engine/src/engine.rs` contains the
same `prefix.push(bytes[i] as char)`. The shipped pack is unaffected (all 15
patterns ASCII — verified by the S1 smoke over every flag). Grade Low for attempt 6
(not a regression; latent fail-open for custom rule authors); recommend `from_utf8`
aware prefix extraction in a follow-up.
