## 6. New findings (none blocking)

1. **MEDIUM/INFO — "allocation-free" scanner claim does not hold for dense-separator runs; per-scan O(n) transient churn.** `SepRun` is created fresh in each `payment_card_candidate_ranges` call (engine.rs:495); its inline array covers ≤16 separators, beyond which `spill` Vec grows by doubling *per scan* (capacity is reused only across runs within the same scan). On inputs where the whole payload is one run (NBSP-only, "9." dense), that is up to **4.3 MB of transient allocation churn per 100KB scan** (17–18 alloc calls), freed at scan end. Latency-invisible (0.64–0.79 ms p50 incl.), linear, not a DoS — but it contradicts the engine.rs:519 comment and is worth fixing in F1.3 (hoist the scratch into the engine / reuse a per-thread buffer) if memory churn matters under concurrency.
2. **INFO — clean-path constant factor up vs attempt 5.** Clean ASCII 100KB p50 0.459 vs 0.332 ms in my attempt-5 probe (+0.13 ms), consistent with the wider 4-alternative phone automaton plus the new per-scan byte scan. Still 2.2× under the 1 ms gate; no action required.
3. **INFO — ContextAnalyzer still runs on every default-pack scan** because `pii.phone_number` keeps 10 contextKeywords (default_pack.rs:168) ⇒ one `to_ascii_lowercase` full-context copy + line-bounds precompute per scan (the 102400-byte alloc above). Present in attempt 5 as well — no regression — but it is now the dominant fixed cost on finding-free scans and the obvious F1.3 optimization (build lazily on first keyword-gated rule match).
4. **Guard honesty (documented, not load-bearing):** `load_test::assert_plan_budgets` enforces the plan budget strictly on **p50** and p99 at 2× (documented `PLAN_CI_TOLERANCE=2.0` for parallel-workspace contention). My serial p99s all sit *under the strict plan budget itself* (0.701<1.0, 0.778<1.0, 0.392<5.0, 1.354<5.0), so no softening affects this verdict. The 100KB phone-list guard remains at the 15 ms CI budget, but the plan-level 1 ms/100KB target is newly enforced by the attempt-6 100KB guards. No plan threshold was moved.
5. **Cross-post (correctness panel, outside my authority):** (a) every rule except `pii.phone_number` now ships `contextKeywords: []` — context gating semantics rest on allowedExamples + validators; the 16/16 P/R gate passed, but this is a precision-semantics change worth explicit sign-off. (b) A separator-connected run whose total digit count lands in 13–19 and passes Luhn+issuer is emitted even when it is a *fragment* of a longer PAN (observed once on a payload truncated mid-PAN: finding span "4000.0566.5566.5556 4", 17 digits). Behavior is consistent with the attempt-5 regex shape and the doc comment's "final segment is emitted last"; flag for the correctness panel's span-semantics review.
